PE@FHIR ULTIMATE MANUAL TESTING GUIDE
=====================================

Purpose
-------
This document is a full manual test script for the PE@FHIR project.
It covers:
- backend readiness
- login and protected routing
- admin workflows
- patient self-registration and self-service
- doctor workflows at Hospital A and Hospital B
- consent lifecycle
- patient-driven push flow
- HIE exchange flow
- audit visibility
- negative and regression checks

Use this as the primary manual QA checklist for a real browser test run.


1. Application Map
------------------
Backend:
- Spring Boot API: http://localhost:8085

Frontends:
- Main frontend: http://localhost:5173
- Hospital A frontend: http://localhost:5174
- Hospital B frontend: http://localhost:5175

Main roles:
- ADMIN
- DOCTOR
- PATIENT

Main routes:
- /login
- /admin/dashboard
- /doctor/dashboard
- /patient/dashboard


2. Preconditions
----------------
Before starting, confirm:
- PostgreSQL is running locally.
- These databases exist:
  - fhir_main
  - hospital_a_db
  - hospital_b_db
- DB credentials match backend/src/main/resources/application.properties:
  - username: fhir_user
  - password: fhir_pass
- Node and npm are installed.
- Maven is installed, or the Maven wrapper works.

Important note:
- The frontend mock fallbacks are disabled in the code, so backend/API failures should surface during testing.

16. HIE Consent and Exchange Flow
---------------------------------
This is the most important end-to-end scenario.

Primary path:
- requester: Doctor at Hospital B
- patient: newly registered patient or seeded patient
- source data owner: Hospital A

TC-HIE-01 Request consent only
Steps:
- Log in as dr_gupta.
- Open Request via HIE.
- Enter the patient ABHA-ID.
- Leave scope as OP_CONSULT or choose extra scopes.
- Purpose:
  - Cross-hospital continuity of care verification
- Click "Request Consent".
Expected:
- status returns consent pending
- consent request ID is shown
- no fatal error

TC-HIE-02 Patient sees pending consent request
Steps:
- Log in as the same patient.
- Open Consent Requests.
Expected:
- new request is visible
- requester ID is visible
- purpose is visible
- requested data types are visible
- status is PENDING

TC-HIE-03 Deny consent path
Steps:
- Deny one pending request at least once during testing.
Expected:
- status becomes DENIED
- patient success/error banner reflects denial
- requester later sees denied/no active consent outcome

TC-HIE-04 Grant consent path
Steps:
- Create a fresh HIE consent request if the first one was denied.
- Log in as patient.
- Grant consent.
- Select at least OP_CONSULT.
Expected:
- request status becomes GRANTED
- patient sees confirmation

TC-HIE-05 Pull after grant
Steps:
- Return to dr_gupta.
- In Request via HIE, use the same ABHA-ID.
- Click Pull Data or rerun exchange as needed.
Expected:
- HIE returns SUCCESS
- FHIR bundle is shown or copied
- Hospital B auto-intakes the bundle where supported
- Hospital B intake list shows the imported consultation

TC-HIE-06 Polling behavior
Steps:
- Initiate another consent request.
- Do not respond immediately as patient.
Expected:
- doctor sees a pending state
- polling does not crash the page
- final state updates when the patient responds

TC-HIE-07 Invalid ABHA-ID through HIE
Steps:
- Use a fake ABHA-ID in the HIE panel.
Expected:
- identity-not-found or failure message appears

- all seeded users can log in

24. Known Project-Specific Notes
--------------------------------
- The backend seeds fresh data only when no users exist.
- Frontend labels and backend seeded hospital names may not be perfectly identical in every place; validate behavior first, label mismatch second.
- Access tokens are stored in localStorage.
- Patient dashboard identity depends on the ABHA-ID claim present in the JWT.
- The patient registration UI uses the patient-specific backend registration endpoint that generates an ABHA-ID automatically.
